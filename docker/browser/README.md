# Browser Runtime image

This directory builds the Browser Runtime image: Debian slim, headful Chromium with a persistent dedicated Profile, a virtual display, two VNC servers and the Runtime supervisor. The full product Compose file (`docker/compose.yaml`) pairs this image with the Gateway. For updates and rollback see [UPDATE-RUNBOOK.md](../../docs/UPDATE-RUNBOOK.md) and [UPDATE-IMPLEMENTATION.md](../../docs/UPDATE-IMPLEMENTATION.md).

Verification status: the Runtime was tested on OrbStack (arm64) and Ubuntu 22.04 (amd64) on its own, and the integrated product only on macOS arm64 with OrbStack using unsigned development releases. There is no integrated amd64 run and no signed release run. See [Known gaps and unverified areas](#known-gaps-and-unverified-areas).

## Files

| File | Purpose |
|---|---|
| `Dockerfile` | Three stages: build the Go Runtime, install Debian packages, assemble the final image |
| `packages.txt` | Package names to install. Exact versions are written to `/usr/share/lensdock/dpkg-manifest.tsv` at build time |
| `fontconfig.reference.conf` | Installed as `/etc/fonts/local.conf`. Maps BCP 47 `zh-Hant` and `zh-Hans` and sets the Emoji fallback |
| `seccomp/chromium.json` | Generated by `tools/gen_seccomp.py`. Do not edit by hand |
| `compose.yaml` | Runs the Runtime alone (read-only root, `cap_drop: ALL`; optional user-namespace sandbox). The full product uses `docker/compose.yaml` |
| `downloads-policy.json` | Installed as a Chromium managed policy so downloads land in the persistent `/data/downloads` |
| `openbox/` | Window manager configuration |

## Standalone use

```bash
mise run image:build      # builds lensdock/runtime:dev; LENSDOCK_ARCH defaults to the host architecture
mise run runtime:init     # creates .lensdock/operator-token and runtime.env (mode 0600)
mise run runtime:up       # starts the Runtime and waits until it is healthy
mise run runtime:down     # stops it; the Profile and Downloads volumes are kept
```

The standalone API is published only on `127.0.0.1:18080`. CDP (9223) and VNC (5900 control, 5901 view-only) listen only on the container's loopback. The image `HEALTHCHECK` probes `/readyz` on the port from `LENSDOCK_LISTEN`, so changing the listen port needs no other change. The product Compose file publishes no Runtime port: the Gateway publishes only `127.0.0.1:18081` and reaches the Runtime over mutual TLS on the internal `control` network.

## Usage mode and policy volume

The Runtime supports `AGENT` (default, shared-browser collaboration) and `NOVNC` (remote browsing without Agent features). Both operate the same headful browser and persistent Profile.

**Choose the initial mode.**

- `LENSDOCK_MODE=NOVNC` or `AGENT` in the container environment. The value is case-insensitive and any other value stops startup. Both Compose files pass `LENSDOCK_MODE: ${LENSDOCK_MODE:-AGENT}`, so set the variable in the environment of the Compose command.
- `--mode NOVNC|AGENT` as container arguments. The image `ENTRYPOINT` is `tini -g -- lensdock-runtime supervise`, so Docker or Compose appends your arguments to it and `--mode` reaches `supervise`. Do not repeat `supervise`. When both are present, the flag overrides `LENSDOCK_MODE`.

```yaml
# Compose: arguments are appended to the ENTRYPOINT
services:
  runtime:
    command: ["--mode", "NOVNC"]
```

```text
docker run [options as in docker/browser/compose.yaml] lensdock/runtime:dev --mode NOVNC
```

**Initial means once.** The flag and the variable apply only until a policy has been saved. After that, the saved mode and pause state win, including after a restart, so a container started with `LENSDOCK_MODE=AGENT` stays `NOVNC` or paused if a user chose that in Settings. Change a saved policy through the Settings page or the workspace API, not through the startup setting.

**Policy directory and security.** The policy is stored in `agent-control.json` inside `/data/runtime` (override with an absolute, clean `LENSDOCK_POLICY_DIR`). Both Compose files mount the dedicated `lensdock-runtime-policy` volume there, and the Dockerfile creates the directory with mode `0700` for UID 10000.

- The supervisor (UID 10000) owns the directory and writes the file with mode `0600`. Chromium and the other browser processes run as UID 10001 and cannot read or write the policy. A `docker exec` check confirmed this for UID 10001 and confirmed `0700` and `0600` ownership by 10000:10000 for UID 10000.
- The directory must already exist as a mount point; the read-only root filesystem never gets it created. A fresh root-owned volume is handed to the supervisor with mode `0700` before privileges are dropped. A directory with any other owner or mode is refused.
- A corrupt policy file stops startup instead of defaulting to `AGENT`. Writes are atomic. If a pause or disable cannot be saved, the running process still fences the Agent for that session, but the saved state may be older after a restart.
- The policy volume is separate from `/data/profile`. Do not remove it with `down -v` or a volume prune: without a saved policy, the initial mode applies again.
- An existing installation must [enroll the policy volume](../../docs/UPDATE-IMPLEMENTATION.md#adding-the-runtime-policy-volume) through the update workflow before upgrading. A Runtime image from before this feature does not read or enforce the policy, so rolling back to one drops the mode and pause restrictions.

## Build behavior

- The Debian base and the Go build image are pinned to multi-arch index digests. `mise run check:pins` confirms the Go version agrees across `mise.toml`, `go.mod` and the Dockerfile.
- `apt-get update` and `apt-get install --no-install-recommends` run in the same `RUN`, and the final image has no curl, wget, compiler or apt index.
- The image must not contain `/usr/lib/chromium/chrome-sandbox`; the build checks this.
- The Runtime binary is built with `CGO_ENABLED=0`, because privilege dropping needs `AllThreadsSyscall`.
- `.dockerignore` is an allow list, so `.lensdock/`, `.git` and `tests/` never enter the build context.

## Process tree and identity

```text
tini -g (PID 1, root)
└─ lensdock-runtime supervise   (root while preparing, then UID/GID 10000)
   ├─ dbus-daemon --session          (UID 10001)
   ├─ Xvfb :99                       (UID 10001, 1920x1080x24)
   ├─ openbox                        (UID 10001)
   ├─ x11vnc :5901 -viewonly -nosel  (UID 10001, view only)
   ├─ x11vnc :5900                   (UID 10001, control)
   └─ chromium                       (UID 10001)
```

1. **Root only prepares.** As root, the supervisor creates `/run/lensdock`, `/run/user/10001` and `/tmp/.X11-unix`, clears stale files, and writes the Xauthority file (exclusive create, mode 0600, no symlink following) before handing it to 10001. It needs only `CAP_CHOWN`: directories are chmod'd before chown so `CAP_FOWNER` is not needed.
2. **The supervisor drops privileges.** The bounding set shrinks to `{SETUID, SETGID}`, supplementary groups are cleared, UID and GID become 10000, `NO_NEW_PRIVS` is set and dumpable is cleared, on every thread. The result is checked against `/proc/self/status`, and startup stops on a mismatch.
3. **Everything else runs as 10001.** X, VNC, Chromium and xclip use a fixed environment allow list with `LANG=en_US.UTF-8` and `FC_LANG=en`. Chromium starts with `--lang=en-US`, so the desktop and browser interfaces default to English. The X cookie lives only in the Xauthority file, never in argv, the environment or logs.
4. **Signals go through a helper.** The supervisor has no `CAP_KILL`, so signals to UID 10001 processes are sent by `lensdock-runtime __signal` (run as 10001, using pidfd or the process group), which avoids signaling a process that reused a PID.
5. **The browser run directory is `0710 10001:10000`.** The supervisor can reach known paths (the Xauthority existence check, the dbus socket gate) but cannot list the directory or read the 0600 cookie.
6. **Secrets are stored as digests.** The container holds only the SHA-256 of the operator token (`LENSDOCK_OPERATOR_TOKEN_SHA256`). Lease tokens exist only as digests in supervisor memory.
7. **Only the API is exposed.** CDP (`127.0.0.1:9223`) and VNC (5900, 5901) stay on the container's loopback. In the product they are reachable only through the Gateway, which requires a valid lease for control (the 5900 path and CDP) and offers the read-only 5901 path to viewers. The UI's `viewOnly` flag is not a security boundary; the Runtime rejects stale leases and connections itself.

## Sandbox

Chromium's renderer sandbox is **off by default** so a fresh install works on any Docker host, including ones that block unprivileged user namespaces. The Runtime passes `--no-sandbox` to Chromium. The container keeps its own isolation: non-root user, read-only root filesystem, `no-new-privileges`, `cap_drop: ALL` and the custom seccomp profile. Without the sandbox, a renderer compromise is limited by that container boundary only.

Turn the sandbox on with `LENSDOCK_CHROMIUM_SANDBOX=true` in `runtime.env` (the state directory's file; the Compose `env_file`), then recreate the Runtime. The value is a Go boolean (`1`, `t`, `true`, `0`, `f`, `false`); anything else is a startup error. The setting is the only way to change the flag: nothing else adds Chromium flags, and unit tests keep `--no-sandbox` out of the enabled argv.

When enabled, the only supported path is an unprivileged user namespace plus the custom seccomp profile `seccomp/chromium.json`. There is no `--privileged`, no `seccomp=unconfined` and no SUID `chrome-sandbox` fallback. Before starting Chromium the supervisor runs a user-namespace preflight. When it fails, the Runtime locks as `SANDBOX_PREFLIGHT_FAILED`, starts no Chromium and does not silently fall back to `--no-sandbox`; turn the setting off to run without it. After startup it proves the sandbox from `/proc`: every renderer must be in a nested PID namespace (at least two `NSpid` levels) and must have more `Seccomp_filters` than the browser process. A bare `Seccomp: 2` proves nothing, because Docker's own filter already makes every process in the container report 2.

`/readyz?detail=1` reports `detail.sandbox.enabled` (the configured setting) and `detail.sandbox.verified` (the `/proc` proof, only attempted when enabled). Disabled is `enabled: false, verified: false`.

`tools/gen_seccomp.py` derives the profile from the pinned moby default profile (commit and sha256 verified) with these differences:

| Syscall | Change |
|---|---|
| `clone` (including the s390 argument position) | Allowed, but not with `CLONE_NEWNS`, `CLONE_NEWUTS`, `CLONE_NEWIPC` or `CLONE_NEWCGROUP`. `NEWUSER`, `NEWPID` and `NEWNET` pass |
| `unshare` | Same flag mask |
| `clone3` | Stays moby's `ERRNO(ENOSYS)`, so glibc falls back to `clone` and the flag mask applies |
| `setns`, `chroot` | Allowed (`chroot` is required in practice) |

A SUID `chrome-sandbox` would need `SYS_ADMIN` and `SYS_CHROOT`, no `no-new-privileges` and the Docker default seccomp profile, so only the user-namespace path is kept. When the pinned moby profile changes, run `mise run seccomp:generate` and repeat `mise run e2e:sandbox-matrix`. The matrix runs both cells with the sandbox enabled: the custom profile must reach Ready, and the Docker default profile must end in `SANDBOX_PREFLIGHT_FAILED` with no Chromium process.

**Host requirements (only with the sandbox enabled).** The host must allow unprivileged user namespaces (`kernel.unprivileged_userns_clone=1` where that sysctl exists, and `user.max_user_namespaces > 0`). On Ubuntu 23.10 and later, `kernel.apparmor_restrict_unprivileged_userns=1` is the default and may block this. That case is untested. If it blocks, the enabled Runtime refuses to become ready with `SANDBOX_PREFLIGHT_FAILED`. Fix the host or its AppArmor profile, or leave the sandbox off.

**Capabilities.** Compose sets `read_only: true` and `no-new-privileges`, then `cap_drop: ALL` and adds back only `CHOWN SETUID SETGID SETPCAP KILL`. Only root's tini keeps `KILL`, to forward the stop signal. After the supervisor drops privileges it has only `SETUID SETGID`. Neither product container is privileged or mounts the Docker socket. The Runtime publishes no port and mounts its credentials read-only.

**Chromium flags.** The argv is fixed. The Runtime does not use `--remote-allow-origins`: the CDP proxy rejects requests that carry an `Origin`, and its upstream connection sends none. It does not disable the GPU by default.

## Network egress

Egress is unrestricted by default. The container uses Docker's default bridge, so Chromium can reach the internet, services on the host, the local network and the cloud metadata address (`169.254.169.254`). In the product Compose file the Runtime sits on both the internal `control` network and the regular `browser-egress` network, so egress is likewise unrestricted. Only the update candidate Runtime is verified on an internal network with no egress route.

This is a deliberate local-use default so you can test development services on the host or LAN (`localhost` inside the container is the container, not the host). No built-in strict mode exists yet. On a shared host or cloud VM, add host-level rules, for example a `DOCKER-USER` iptables chain on Linux that blocks `169.254.0.0/16` and host addresses. OrbStack and Docker Desktop route traffic through a VM, where such host rules do not apply.

## Fonts and text input

- Child processes use `LANG=en_US.UTF-8` and `FC_LANG=en`. Generic families resolve to Latin Noto Sans, allowing Chromium to choose CJK fonts by each element's `lang`. A CJK generic default can swallow Japanese and Korean glyph selection because the first CJK font covers those characters too.
- Fontconfig 2.15 does not understand BCP 47 script subtags, so `zh-Hant*` and `zh-Hans*` would fall to the default JP. `fontconfig.reference.conf` maps `zh-hant` to `zh-tw` and `zh-hans` to `zh-cn` before the Noto CJK rules apply.
- Emoji, including skin tones, flags, VS16 and ZWJ sequences, render as single Noto Color Emoji glyphs.
- Text input uses `PUT /clipboard` with a HUMAN or AGENT lease followed by Ctrl+V on control VNC. Before returning 204, the Runtime reads CLIPBOARD back with `xclip -out` and requires the same bytes, waiting at most 2 seconds. It answers 502 `UPSTREAM_UNAVAILABLE` when the owner exits first or the content never matches. The clipboard is cleared when its lease ends. If another program takes the selection after the 204, the paste is that program's content; this is outside the guarantee.
- RFB `ClientCutText` is not used. x11vnc 0.9.17 receives it, but Chromium never gets the content, ASCII included, and the protocol defines the text as Latin-1, so it cannot carry UTF-8.

## VNC

Two x11vnc instances read the same display: 5900 for lease-bound control and 5901 with `-viewonly -nosel` for viewing. The Runtime enforces read-only access independently of the web UI. HUMAN and AGENT leases can use control VNC; Agent commands are also subject to mode and pause.

`lensdock desktop` connects through this fenced path to capture the full screen and send pointer, keyboard and UTF-8 input. It reaches Chromium's address bar, menus, native dialogs and extension interfaces without a DOM target. A fresh screenshot provides the coordinates; the CLI checks the live desktop bounds. `lensdock cdp bridge --lease-file-out FILE` lets CDP and native desktop commands share one Agent lease. Both channels close when that lease ends.

Right-click the empty desktop and choose **Restore browser** to recover a minimized
or missing browser window. Openbox invokes the fixed `lensdock-runtime restore-browser`
command. It uses the existing loopback CDP endpoint to restore and activate a page
window, or creates an `about:blank` window when none exists. It does not launch a
second Chromium, reset the Profile or change webpage context menus. Input still
requires a valid control lease; the first gesture used to acquire control is consumed.

## Clean stop

The supervisor sends `Browser.close` first (waiting up to 3 seconds) and falls back to signals, because the SIGTERM path does not remove the Profile locks. Integrated runs showed `profile.exit_type` of `Normal` and no `Singleton*` locks, and restart after `SIGKILL` was also exercised. The update flow judges a checkpoint clean by the same conditions (exit code, locks, `profile.exit_type`, SQLite journal).

## Known gaps and unverified areas

- Hosts with `apparmor_restrict_unprivileged_userns=1` (Ubuntu 23.10 and later), rootless Docker, Podman and cgroup v1.
- The screen behavior of Chromium's "did not shut down correctly" prompt.
- The GPU and software-rendering support matrix, 4K, multiple screens and HiDPI.
- An integrated amd64 run.

## Agent browser operations

An Agent lease grants high-trust control of this browser. The CDP proxy permits `Browser.close` and `Extensions.*`. An unpacked extension must exist at the requested path inside the container. `Target.exposeDevToolsProtocol` remains blocked because its page binding would outlive the fenced connection; nested `Target.sendMessageToTarget` is blocked to prevent bypassing that check. Flattened target sessions remain supported. Closing Chromium causes a restart and invalidates old leases.

For extensions that use Native Messaging, add the host executable and its dependencies to a derived Runtime image. Register its manifest under `/etc/chromium/native-messaging-hosts/`, with a `0755` directory and a readable manifest such as `0644`. Verify access as the browser user, UID `10001`, rather than root: a directory without execute permission makes Chromium report `Specified native messaging host not found` even when the manifest exists. Keep unpacked extensions in a persistent path so they survive container replacement, and deploy the derived image through the paired update workflow.

## Data lifetime and removal

Host-side age expiry removes only unreferenced update data, not the active Profile,
keyring, runtime policy, downloads or feedback. The Runtime cannot run Docker cleanup.
For CLI removal or permanent workspace deletion, follow
[Uninstall and data removal](../../docs/UPDATE-RUNBOOK.md#uninstall-and-data-removal).
Keep the matching Profile, keyring and database together for a later restore.
